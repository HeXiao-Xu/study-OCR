## 2. 决策

### 2.1 测试与演示里的 OCR

- `test_e2e_flow.py` 用**确定性假 OCR 引擎**（`tests/test_ocr_pipeline.py` 的 `FakeEngine` + `_vat_digital_lines_full`），
  但**上传接口、OCR 作业执行路径、字段落库、确认接口、密码链路、MinIO（FakeStorage）、Redis（内存凭据）全是真的**。
  理由：真 Paddle 推理要在测试里加载模型（数秒 + 字体/环境敏感），会把"联调卡"变成 flaky；真 OCR 的覆盖已在
  S1/S3 的 100+ 用例与 `scripts/ocr_baseline.py`。
- `scripts/e2e_demo.py` 同样用**演示桩引擎**（脚本内定义，输出固定票面），并**显式打印**
  `mode=mock-ocr`；密码链路、MinIO、Redis、DB 全真。论文/答辩演示时如实说明"OCR 用确定性桩，密码链路真实"。

### 2.2 全链路（与任务卡一致）

```
登录(submitter) → 上传 → OCR(假引擎) → 确认字段 → 建单 → 签名 → 提交(加密/信封)
→ 登录(reviewer) → 验签 → 解密预览 → approve → 登录(admin) → archive
```

- 上传：`POST /invoices/upload`（202，FakeQueue 只记录 job_id，不真入队）；
- OCR：`job_service.execute_job_attempt(... handler=run_pipeline(deps=FakeEngine))`（真实作业终态/回滚路径）；
- 确认：`POST /invoices/{id}/confirm`；为摆脱"置信度阈值"对假引擎的耦合，测试里先把字段标成
  `confirmed=true/need_review=false`（等价 UI 逐字段勾选，**仍走确认接口**）；
- 建单：`POST /reports` + `POST /reports/{id}/items`（金额取票面合计）；
- 签名/提交：`POST /reports/{id}/sign`（演示口令）→ `POST /reports/{id}/submit`；
- 财务：`verify` → `decrypt` → `GET preview/{token}` / `files/{id}` → `review`（approve）；
- 归档：`POST /admin/reports/{id}/archive`（admin，`confirm=true`）。

### 2.3 异常码清单（以 API.md §10 为准）

| 场景 | 期望 | 说明 |
|---|---|---|
| 无 token 调财务接口 | `401/40101` | 认证层 |
| submitter 调 `/finance/pending` | `403/40301` | 角色级 |
| 已提交后用**新幂等键**再提交 | `409/40900` | 同键重复是 200 `duplicated`（S5-2 契约），不是 409 |
| 同影像再次上传 | `409/40901` | 去重命中 |
| 同一票据加进第二张报销单 | `409/40901` | 一票一单 |
| 未验签直接 approve | `409/40900` + `reason_code=verify_token_invalid` | S5-5 |
| 篡改签名域后 verify | `409/50021` + `reason_code∈{bad_signature,digest_mismatch}` | S5-4 |
| 非 approved 直接 archive | `409/40900` | S5-6 |
| 签名口令错误 | `422/42200` | S5-2 统一文案 |
| 归档缺 confirm | `422/42202` | S5-6 |

> **API.md 修正**：§10 的 42202 典型场景原写"审批未带有效 verify_token"，与 §5 review 契约（409）冲突；
> 本卡按实现改正为"修改金额字段未带 confirm_amount；归档未带 confirm"，并注明审批缺 token 是 409。

### 2.4 并发 approve

- 建一张 `submitted` 单并 verify 拿 token；
- 两个独立 `TestClient`（同一 app/session_factory/内存凭据）在两个线程同时 `POST /review`（同一 version/token）；
- 断言 HTTP 状态集合 `{200, 409}`、`review_logs` 恰好 1 行、单据 `approved`。
- 行锁已在 S5-5 实现，本卡验证**从 HTTP 进入**也成立。

### 2.5 安全不变量（任务卡 ④）

- `invoice_files.is_cipher=true`，`storage_key` 指向的对象**不是 JPEG/PNG 明文**（没有 `\xff\xd8` / `\x89PNG` 头）；
- `information_schema` 里 `invoices/invoice_files/report_forms` **没有 `bytea` 列**（库里不存影像字节）；
- 用财务私钥 `open_sealed` 单据信封与每个文件信封，明文 sha256 分别等于 `envelopes.payload_sha256`
  与 `invoice_files.sha256`（`open_sealed` 内部已校验，测试再显式断言一次）；
- 响应体（verify/decrypt/export）不含 `ciphertext_b64`/`wrapped_key_b64`/`storage_key`。

## 3. 演示脚本

`scripts/e2e_demo.py`：

```bash
python scripts/e2e_demo.py                # 开发库 + 真 MinIO/Redis；跑完清理业务行，保留审计
python scripts/e2e_demo.py --keep         # 保留业务行，便于 UI 查看
python scripts/e2e_demo.py --export-pass 'demo-export-1234'
```

- 依赖本地已有的 `alice/bob/root` 与已登记身份（HANDOFF §2.1）；缺失时打印 `scripts/create_user.py` /
  `scripts/register_identity.py` 指引并退出码 2；
- 每步打印 `[step] <动作> -> HTTP <code> trace_id=<X-Trace-Id>`；最后打印归档号、验证链结果与清理结果；
- 退出码：0 成功；2 环境不满足；1 断言失败（不吞异常）。

## 5. 已知限制

- e2e 的 OCR 是**确定性桩**（测试与 demo），不是真 Paddle；真 OCR 的端到端由 S3 测试与基线脚本覆盖；
- demo 会写开发库并清理（审计只增不减，跑几次就多几行；`AUDIT_HMAC_KEY` 不要换）；
- 并发只测"同时 approve"，不压测 verify/decrypt；
- 归档包导出不重复测（S5-6 已覆盖），e2e 只验证"归档成功"。
