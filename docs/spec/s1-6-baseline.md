# S1-6 端到端基线脚本与指标计算 — 设计（spec）

> 状态：已实现（按用户"继续"直接实现；要改的点直接说，我回退）

## 1. 目标

一条命令跑出论文可用的数字，并且**可复跑**：

```
python scripts/ocr_baseline.py --compare-preprocess
```

产出 `backend/eval/results/baseline_<时间戳>.json`（不覆盖历史）+ `baseline_report.md`（可直接贴论文）。

## 2. 指标口径（以 `docs/EVAL.md` §2 为准，实现集中在 `backend/eval/metrics.py`）

| 指标 | 定义 |
|---|---|
| 检测 P / R / Hmean | **覆盖匹配**：标注框被某预测框 IoU≥0.5 **或** 85% 面积被其包含即命中；预测框需 IoU≥0.5 或包含某标注 50% 才不算误检 |
| 字符准确率 | `1 − 编辑距离(预测, 标注)/标注长度`，按行拼接后计算 |
| 字段级准确率 | 单字段精确匹配（金额用 Decimal，容差 0.01）；分母 = 该字段有标注的样本数 |
| 整单正确率 | 一张票的**所有标注字段**都对 |
| 待确认率 / 低置信命中率 | 置信度 < 0.7 的字段占比 / 其中确实错误的比例 |
| 耗时 | preprocess / ocr / layout / extract 各阶段 P50·P95 |

**口径必须在论文里写清楚的两点**：
1. **整单正确率必然远低于字段级准确率**（12 个字段各 0.9 → 整单约 0.28），两个数要同时报；
2. 检测用**覆盖匹配**而不是纯 IoU：标注是**元素级**（一行被画成多个单元格框），引擎输出是**行级**，
   纯 IoU 会把"把一行合成一个框"判成大量漏检（实测 Hmean 0.09 → 0.95）。

## 3. 坐标系（最容易踩的坑）

标注框在**原图坐标**，而 OCR 跑在**透视校正后**的图上。基线脚本用 `to_original` 的逆矩阵
把标注框映射到校正图再匹配——不换坐标系，IoU 恒为 0。

## 4. 配置（`backend/eval/configs/baseline.yaml`）

`preprocess`（5 个开关 + max_side）、`ocr`（unclip_ratio / limit_side_len / angle_cls / drop_score）、
`metrics`（IoU 阈值 / 待确认阈值）、`rules`（字段规则路径）。S6 复制本文件改参数即可复现实验。

## 5. 实测（60 张合成集，CPU）

| 指标 | 预处理开 | 预处理关 |
|---|---|---|
| 检测 Hmean | 0.948 | **0.974** |
| 字符准确率 | 0.816 | **0.828** |
| 字段级准确率 | **0.856** | 0.847 |
| 整单正确率 | 0.500 | **0.517** |
| 待确认率 / 低置信命中率 | 0.110 / 0.136 | 0.116 / 0.152 |

耗时（预处理开）：preprocess P50 111ms、ocr P50 1422ms、layout 52ms、extract 1ms，全链路 P50 1591ms。

## 6. 这组数字说明了什么（如实记录）

1. **预处理对"定位"是负收益**（Hmean 0.974 → 0.948）、对"识别/字段"是正收益（字段 0.847 → 0.856）。
   解释：合成集的图本来就没躺倒，透视重采样只带来插值损失；而它对光照/背景的归一化帮助了字段抽取。
   **这正是 S6 要做的消融**，不能只报一个"预处理有用"的结论。
2. **整单正确率只有 0.50**，瓶颈在 `taxi_ticket`（0.20）与 `vat_general`（0.35）：
   小票字小、旧版票合计行被印章压住。字段级 0.856 与整单 0.500 的关系已按 EVAL 的要求同时报告。
3. **字段短板仍是 amount(0.60)/tax(0.567)**，与 S1-5 的结论一致——不是评测口径问题。
